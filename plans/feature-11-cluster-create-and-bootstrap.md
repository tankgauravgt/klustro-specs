# Feature 11 — Cluster creation and bootstrap

| | |
|---|---|
| Increment | 11 |
| Depends on | 01–10 |
| Unblocks | 12, 13, 27, 28 |
| Spec refs | §5.2 (Cluster), §10.10, §12.1–12.4, §16.1 |

## Goal

Stand up a real, HA-capable Kubernetes cluster on customer hardware over the mesh — the point at which Klustro stops being a network manager and starts being a cluster manager.

At the end of this increment a customer can create a cluster, assign servers and workers, and have a healthy cluster running on their own machines.

## In scope

- Cluster entity, options and state machine.
- Creation, including the network-provisioning barrier.
- Node assignment and its policy ordering.
- Embedded etcd bootstrap and the join sequence.
- Server counts, quorum protection and etcd tuning.
- Cluster token handling and node configuration.

## Out of scope

- The API entry point, service advertising and kubeconfig (Feature 12).
- Drain, removal and deletion (Feature 13).
- Upgrades (Feature 27) and snapshots (Feature 28).
- Cluster templates (later).

## Requirements

**Cluster entity and creation**

R1. A cluster belongs to exactly one project.
R2. A cluster has an id, project, display name, Kubernetes version, creation options, status, service name derived from its UUIDv7, a bootstrap node reference, and etcd tuning values.
R3. Creation options and their defaults: Kubernetes version (latest of the supported three minor versions); whether servers are dedicated (tainted) — default off; which bundled components are disabled — default none; cluster and service CIDR — defaults as specified; snapshot schedule and retention — default every 12 hours, keep 5.
R4. Cluster and service CIDRs must not overlap the mesh provider's address range. A conflicting selection is refused with an explanatory message.
R5. Cluster creation is refused beyond the plan's cluster limit and while the account's lifecycle state forbids it.

**State machine and the network barrier**

R6. Cluster states are: network provisioning, waiting for servers, bootstrapping, ready, degraded, upgrading, deleting.
R7. A newly created cluster enters network provisioning and becomes eligible for node assignment only after a policy revision containing its tags, system rules, auto-approval entry and service object has been applied.
R8. The customer-facing UI shows this wait as normal preparation, not as an error or a stall.
R9. A cluster is degraded when etcd is unhealthy, quorum is at risk, or a server's API is not ready.

**Node assignment**

R10. Assigning an unassigned node to a cluster requires the assignment action and names a role of server or agent.
R11. Assignment is ordered: a policy run with the new tags completes first, then the device is retagged, then cluster software is installed and the node joins.
R12. A node belongs to at most one cluster and to exactly one project.
R13. Moving a node between projects requires removal and re-enrolment.
R14. A node cannot be assigned while the cluster is not yet past network provisioning.

**Bootstrap and joining**

R15. The first server assigned becomes the cluster's bootstrap node and initialises the cluster's datastore.
R16. This applies to single-server clusters too, so that growing to three servers later never requires a datastore migration.
R17. All other servers and all workers wait until the bootstrap server is ready and the cluster's API is reachable through the service, then join through it.
R18. The cluster's shared secret is generated by Klustro, stored encrypted, and delivered only to enrolled agents over their authenticated channel.
R19. Agents write the node's cluster configuration from values supplied by Klustro, including: whether this node bootstraps; the API endpoint to join; the cluster secret; the node name derived from its UUIDv7; the node's mesh address; the mesh interface to use for overlay networking; the API endpoint's TLS subject alternative names; node labels identifying the Klustro node and cluster; the API server's OIDC settings pointing at Klustro's issuer with the cluster's client id; and the etcd snapshot schedule and retention.
R20. Overlay networking MTU is derived from the mesh interface, not hardcoded.
R21. A node that fails to install enters a failed state with logs and a retry path, and does not silently remain in installing.

**Server count and quorum**

R22. Server counts of 1 through 5 are permitted; more than 5 is rejected.
R23. One and two servers are shown as not highly available; three is recommended; two and four are shown as transitional with a warning to add or remove a server.
R24. Removing, draining or upgrading a server is refused if it would leave fewer healthy datastore members than quorum requires, with a message stating the arithmetic.
R25. Quorum protection must be enforced as a single shared rule used by every operation that could reduce healthy members.

**etcd over the mesh**

R26. Agents report round-trip time and transport type (direct or relayed) to every peer server.
R27. A relayed path between two servers produces a cluster warning.
R28. Round-trip time above the configured threshold between servers produces a warning.
R29. Datastore consensus timing values are derived from measured round-trip time when servers join: defaults when latency is low, and scaled up when the measured high-percentile latency exceeds the threshold, using Klustro's documented formula.

**Visibility**

R30. A cluster page shows status, version, members, datastore health, quorum status and per-node roles.
R31. Cluster creation, node assignment, bootstrap, successful join and failure transitions are audited.

## Acceptance criteria

- A customer creates a cluster, assigns one server and two workers, and reaches a ready cluster with a healthy datastore.
- Assignment is refused before the cluster's policy revision is applied.
- A second server joins and the cluster becomes HA-capable without any migration.
- A node with a conflicting CIDR configuration is refused with a clear message.
- Attempting to remove a server when it would break quorum is refused with the arithmetic shown.
- A relayed path between two servers raises a visible cluster warning.
- Single-server to three-server growth is verified end to end.
